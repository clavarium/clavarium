Clavarium

A conversation is a VM with a terminal in it. Everything else is a folder. Agreed architecture; the plan waits for a go.

Conversation

= one Multipass VM + one command running in tmux. The command is a setting: Claude Code, OpenCode, OpenHands, a shell.

Screen

= the raw terminal, in the browser. No chat layer, no cards, no parsing of the tool's output.

Resource

= a folder in the VM. A directory, a git repository, a mailbox, a secret: all of them arrive as files.

When does a VM stop?

SituationWhat happensWhy
You close the page, lock the phone, lose the networkNothing. The tool keeps running in its VMlong jobs must finish without a screen attached
The tool has exitedthe VM is stopped after a short delaynothing runs any more; memory is returned, the disk is kept
You press Sleepthe VM is suspended, the tool frozen as it isyour decision, when you know it is waiting for you
The tool is running and nobody watchesNothing, in version 1. No automatic sleeptelling “thinking for an hour” from “idle” cannot be done safely without reading the tool; a wrong guess would freeze real work
You open the conversation againthe VM starts or wakes; the tool is started again if neededone gesture

Later, if wanted: an opt-in automatic sleep per conversation, on strict signs only (no screen attached, no terminal output and no processor use for a long, chosen time).

Five walls, from outside in

0 · Relaypublic, but blind: it carries encrypted bytes to a tunnel that home opened. Compromised, it can cut the line, not read it.
1 · Edge, at homeTLS ends here; OIDC sign-on (identity provider + auth proxy), one operator. No inbound port, no subdomain.
2 · Host processlistens on loopback, accepts identity from the auth proxy only; unprivileged user; may only call a wrapper that accepts a fixed list of multipass verbs.
3 · VM boundarythe agent is root inside and sees nothing of the host.
4 · Mountsthe only doors: chosen per conversation, each one read-only or read-write; read-only is enforced by the host.

Two kinds of secret

Stays on the host

The host acts with it: pushes a branch, syncs a mailbox. A compromised agent cannot leak it.

git deploy key · IMAP password · OAuth refresh tokens

Handed to the agent

The tool needs it to run. Assume the agent can read and send it anywhere. Give narrow, revocable keys only.

model API key for OpenHands · a test database password

Read-only is enforced on the host

The agent is root in its VM, so a “read-only” flag inside the VM would be worth nothing. The host exposes a read-only view of the folder and mounts that view.

Checked: the Multipass mount command has no read-only option of its own. The host-side view is the first thing to prove on a real VM.

Two writers, one folder

Allowed. Files are shared live; two agents editing the same file at once will overwrite each other, as two people would. For code, a git resource gives each conversation its own branch instead.

What “it becomes theirs” implies

They are root in that VM too

Whoever holds the terminal can do what the agent can: read every attached resource and every handed secret. Share a conversation only with what you would give that person.

The tool's account travels with it

A conversation logged into your Claude subscription is used on your subscription by whoever you share it with. For someone else, prefer a conversation on an open model, or their own login.

Result

The hooks and the two checkers (assistant names, identifying shapes) are public and reusable as they are. One piece is missing on purpose: the list of forbidden words, which must be supplied from outside the repository.

English only

Code, comments (plain ASCII, the why), docs, commit messages, default UI strings. Other languages are label files.

Nothing identifies anyone

No person, company, domain, machine path. example.com everywhere.

Fix the cause, never the check

A commit is cheap, a push is gated. No guard without a cheap way to be right.

One line each

Three commands exist, and no fourth: start the appliance, install on Ubuntu, set up the relay.

Parameters, not prompts

Everything a command needs is on its line: domain, operator email, relay address. It never stops to ask. Run twice, it ends in the same state.

Strict about the ground

The script refuses any system other than the one it names, before touching anything, and says why.
